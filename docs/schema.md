# Thinkback database schema

All primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY`. All timestamps are `TIMESTAMPTZ`.
"Enums" are `TEXT` plus a named `CHECK` constraint. `NULL` is only allowed where stated.

The tables fall into three groups: **content** (what the learner studies), **learning activity**
(what the learner does), and **analytics input** (the raw event log).

## Content

### users
One row per learner. Everything else hangs off a user. Just `id`, `display_name`, `created_at` for now.

### documents
A source the learner uploaded (a PDF or pasted text). Needed so we know where chunks and concepts came from.
- `source_type` CHECK in `pdf`, `text`. `status` CHECK in `uploaded`, `processing`, `ready`, `failed` (default `uploaded`); `error_message` explains a failure.
- `content_hash` + `UNIQUE(user_id, content_hash)`: the same learner cannot upload the identical content twice.
- `original_filename`, `file_path`, `page_count` are NULL for pasted text.

### chunks
A document cut into passages. Hints must cite real source passages, so we store them.
- `ON DELETE CASCADE` from documents. `UNIQUE(document_id, chunk_index)` keeps ordering unambiguous.
- `page_start`, `page_end`, `token_count` are optional metadata.

### concepts
An idea extracted from a document that can be practised (e.g. "LEFT JOIN").
- `source_chunk_ids BIGINT[]`: which chunks support it (a deliberate simplification, see LEARNING.md).
- `origin` CHECK in `model`, `user` (default `model`): did the AI propose it or did the learner add it. `is_active` lets a learner hide one without deleting history.
- `model`, `prompt_version`: which model/prompt produced it (NULL for user-made concepts).
- `UNIQUE(document_id, name)`; cascades from documents.

### questions
A practice question for one concept.
- `question_type` CHECK in `explain`, `apply`, `predict`.
- `rubric JSONB`: the points a good answer must cover (used by the grader, never shown to the learner).
- `misconceptions JSONB` (nullable): common wrong beliefs the grader can look for.
- `model`, `prompt_version`: provenance, so we can compare prompt versions later. Cascades from concepts.

## Learning activity

### attempts
One learner working on one question, from start to finish. This is the central table: hints and answers attach to it.
- `status` CHECK in `in_progress`, `completed`, `abandoned` (default `in_progress`).
- `max_hint_level SMALLINT` CHECK 0-4 (default 0): the deepest hint used. This is the main "independence" signal.
- `revealed_at`: set if the learner gave up and saw the answer.
- `effective_score NUMERIC(3,2)` CHECK 0-1: the final score after adjusting for hints/reveal. Distinct from the raw `rubric_score` on an answer.

### answers
What the learner submitted for an attempt, and how it was graded. A separate table because an attempt can have several submissions.
- `rubric_score NUMERIC(3,2)` CHECK 0-1, `points_covered` / `points_missed` JSONB, `misconception`, `feedback`: the grader output. All NULL until graded.
- `grader_model`, `grader_prompt_version`: grader provenance. `submitted_at` vs `graded_at` show grading latency. Cascades from attempts.

### hint_requests
Each hint given during an attempt (levels 1-4, increasingly direct).
- `level` CHECK 1-4; `UNIQUE(attempt_id, level)` means asking for the same level again returns the stored hint instead of generating a new one.
- `cited_chunk_ids BIGINT[]`: source passages the hint is grounded in.
- `leak_check_passed` / `regenerated`: whether the hint was checked for giving away the answer, and whether it had to be regenerated.
- `model`, `prompt_version`. Cascades from attempts.

### concept_mastery
Current mastery estimate of one user for one concept. Composite PK `(user_id, concept_id)`.
- `mastery NUMERIC(4,3)` CHECK 0-1, `attempt_count`, `last_misconception`, `updated_at`.
- This is a derived, fast-to-read summary; the history lives in attempts/answers/events. Cascades from concepts.

## Analytics input

### events_raw
An append-only log of things that happened. The bronze layer of the analytics pipeline reads from here.
- `event_type` CHECK in `document_uploaded`, `concepts_extracted`, `question_served`, `hint_requested`, `answer_submitted`, `answer_graded`, `answer_revealed`.
- `document_id`, `concept_id`, `question_id`, `attempt_id` are plain `BIGINT NULL` with **no foreign keys** (see LEARNING.md). `user_id` is the one real FK.
- `payload JSONB` (default `{}`) holds event-specific details; `schema_version` lets payload shape evolve; `occurred_at` defaults to `now()`.
- Indexes: `(user_id, occurred_at)` for per-learner timelines, `(event_type, occurred_at)` for per-event-type scans.

## Foreign key summary
| child | parent | on delete |
|---|---|---|
| documents.user_id | users | no action |
| chunks.document_id | documents | CASCADE |
| concepts.document_id | documents | CASCADE |
| questions.concept_id | concepts | CASCADE |
| attempts.user_id / question_id | users / questions | no action |
| answers.attempt_id | attempts | CASCADE |
| hint_requests.attempt_id | attempts | CASCADE |
| concept_mastery.user_id | users | no action |
| concept_mastery.concept_id | concepts | CASCADE |
| events_raw.user_id | users | no action |

Note that `attempts.question_id` has no cascade: deleting a question that has attempts is blocked, which protects learning history.
